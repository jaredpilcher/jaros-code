# Jarify: Governance & Convergence Loop

A recurring self-governance heartbeat for any Jarify-governed repository (a repo with a `.jarify/`
directory and a Prime Directive folder `PRIME-*/intent.md`). Run it on a fixed cadence (~every 30
minutes) to keep specs, intents, and code in **absolute compliance** AND to **continuously drive the
project forward** — discovering and queuing the next change. It is the autonomous loop that maintains
and advances the project between human messages. It is repo-agnostic: it works from the `.jarify/`
structure and the Jarify skills/agents, so it reproduces in a restarted session or a brand-new repo.

## Jarify is the HARNESS — use the Jarify skills for EVERYTHING (standing, non-negotiable)

**Jarify is HOW the model is harnessed to build the system. EVERY change flows through the Jarify skills
and agents — always, no ad-hoc edits.** `jarify-manage-specs` / `jarify-manage-tasks` /
`jarify-manage-links` / `jarify-manage-roadmap` for the governance artifacts → **jarify-builder**
(implements one task, tests) → **jarify-architect** (validates + commits). Spec + code in the same commit
(spec-first; stale specs are defects). This is the mechanism of convergence itself — reaching for an
ad-hoc edit outside the Jarify workflow is a failure of the loop. **Constantly remind yourself of this
every tick, and carry the reminder into the loop's self-re-arm prompt** (see Cadence).

**The `.jarify/ROADMAP.md` is what we EXECUTE — near AND far term — WITH the Jarify skills — to converge
on the intent of the Prime Directive.** The convergence hierarchy is code → requirements → each spec's
`intent.md` → the Prime Directive; every roadmap item traces up to it. Working the roadmap's top `NOW`
item THROUGH the Jarify workflow (specs/tasks → builder → architect) is the loop's core act.

## The pursuit is UNBOUNDED — never done, never satisfied

The Prime Directive's intent is an **asymptote, not a finish line**: we will **never fully reach it, and
we must never be satisfied or declare the work "done."** Every cycle marches the system *closer* to that
intent without ever arriving — that is the entire point of the loop. **"Good enough," "done,"
"complete," "saturated," and "at the ceiling" are FORBIDDEN conclusions**; reaching for any of them is
the failure mode itself. There is ALWAYS a next change that brings the system nearer to the intent, so
the loop runs forever, always iterating toward it. Compliance keeps the march honest; convergence keeps
it moving; the march toward the intent never ends. If a cycle ever feels finished, look harder — the
gap to the intent is never zero.

## The convergence hierarchy — everything points at the Prime Directive

Every tick, the loop keeps this hierarchy CONVERGENT, top to bottom, and it is the loop's core job:

```
        Prime Directive intent (PRIME-*/intent.md)   ← the SUPREME north star; never overridden
                    ▲  every spec converges toward it (never contradicts it)
            each spec's intent (intent.md — every spec has one)
                    ▲  requirements + code converge toward the spec's intent (compliance)
        requirements → tasks → code   (traceable via index.json)
                    ▲
        ROADMAP  — the prioritized forward plan; EVERY item must trace UP to the Prime Directive intent
                    ▲  maintained + regenerated by
                THIS LOOP  (auto-steer)
```

The loop guarantees convergence with three continuous actions, every tick:
1. **Compliance (upward, code→spec):** code actually satisfies its spec's requirements/intent (step 1).
2. **Conflict resolution (spec→Prime Directive):** resolve any spec/spec or spec/intent conflict by
   intent, **Prime Directive supreme** — it always wins; fix the other side. Generate a missing spec
   intent consistent with the Prime Directive (step 2). No spec is allowed to drift from the Directive.
3. **Roadmap generation (close the gap to the intent):** the loop continuously measures the GAP between
   the current system and the Prime Directive intent (via GAP-MAP + the scoreboard) and **ADDS/RE-PRIORITIZES
   roadmap items to cover that gap** — new specs/requirements that make the system converge further. This
   is the engine that keeps the roadmap growing toward the intent: as long as a gap to the Directive
   exists (always — it is an asymptote), the loop auto-steers MORE onto the roadmap. It never stops
   converging and never declares "done" (step 3). Every roadmap item, when picked up, becomes specs/tasks
   through the Jarify workflow, so the whole tree stays traceable back to the one Prime Directive.

## When to use
- To stand up or run the standing governance loop in any Jarify repo.
- Every ~30 minutes while working autonomously; re-arm yourself so it continues unattended.

## The cycle — do ALL of these every tick

### 1. Compliance audit (spec ↔ code)
Walk every `.jarify/<SPEC>/`. Validate that the code TIED to each spec (via `index.json` traceability)
actually satisfies its `requirements.md` — the `### [REQ-x]` blocks and their acceptance criteria — and
that the traceability is accurate (referenced files/anchors exist). Do a fast STRUCTURAL sweep every
tick — **EVERY spec folder MUST contain all five files: `intent.md`, `design.md`, `requirements.md`,
`tasks.md`, `index.json`** (owner directive 2026-07-04; the Prime Directive folder is the sole
exception — ONLY intent+design). Also check `### [REQ-x]` format, frontmatter `status` sane, referenced
files exist. If a spec is MISSING `intent.md` or `design.md`, BACKFILL it via `jarify-manage-specs`
(author the intent it clearly serves — consistent with the Prime Directive — plus a design with an ASCII
diagram). PLUS ONE rotating DEEP semantic check (does the code actually meet a spec's criteria) —
coverage over time, not a 12-spec deep audit every tick. FIX any non-compliance.

### 2. Conflict resolution (specs ↔ intents ↔ Prime Directive)
Detect conflicts BETWEEN specs, and between a spec and its own requirements. RESOLVE automatically by
the spec's INTENT (`intent.md`). **If a spec has no intent, read its requirements and GENERATE the
intent you judge it to be** (consistent with the Prime Directive). **The PRIME DIRECTIVE's intent is
the supreme, ruling authority — it must NEVER be overridden.** Any conflict with the Prime Directive →
the Prime Directive wins; fix the other side. Never silently resolve a tenet conflict — if a change
would violate the Prime Directive, STOP and flag it.

### 3. Auto-steer — proactively DRIVE the next change (convergence)
This loop does not just maintain compliance; it OWNS moving the project forward between human messages.
Each tick, run the convergence step and ACT on it:
- **DRIVE FROM THE ROADMAP (`.jarify/ROADMAP.md`) — the LONGER-HORIZON forward plan.** The Roadmap and
  the task list are TWO COMPLEMENTARY LAYERS, not competitors: the **Roadmap is the longer-seeking plan**
  (which specs/requirements are coming, over horizons) and the **task list is the SHORT-TERM immediate
  work, executed exactly as before** (TaskCreate/TaskUpdate → builder → architect). The Roadmap FEEDS the
  tasks: when its top `NOW` item becomes the immediate work, DECOMPOSE it into concrete tasks
  (`jarify-manage-tasks` / TaskCreate) and execute them the normal way — the roadmap never replaces or
  bypasses the task workflow, it steers what the next tasks should be. Every tick, MAINTAIN the roadmap via
  the `jarify-manage-roadmap` skill —
  mark shipped items `LANDED` (with commit), park blocked items with a reason, ensure `NOW` is
  non-empty by promoting from `NEXT`, and **when the plan thins, REGENERATE the next horizon** from
  the Prime Directive intent + the measured gaps (the pursuit is unbounded — there is ALWAYS a next
  horizon; never leave it empty or conclude "done"). When a `NOW`/`NEXT` item is a spec/requirement
  that doesn't exist yet, create it via `jarify-manage-specs`/`-tasks` when you pick it up, then
  implement through builder→architect. If the repo has NO Roadmap yet, CREATE one (`jarify-manage-roadmap`)
  from the intent + gaps as an early act — it is how the loop and the human stay aligned on what's coming.
- **MEASURE → DIAGNOSE → DISCOVER → PLACE → WIRE → RE-MEASURE → PRUNE.** Measure honestly (held-out, no
  gaming); diagnose the real failure (probe the raw output); discover the next grain/change; place it
  (a judgement → an agent; a deterministic effect → a tool, per the two-plane rule); wire it (no
  orphans); re-measure; prune anything net-negative.
- **BUILD, don't defer.** If you catch yourself DESCRIBING the next improvement instead of building it
  ("teed up for next"), that IS the failure mode — build it now (through the Jarify workflow) and
  measure it this cycle.
- **Maintain a LIVE TO-DO LIST** (the task list / TaskCreate-TaskList-TaskUpdate). CHECK and UPDATE it
  EVERY tick — mark done, add newly-discovered work, re-prioritize by impact×tractability (structural /
  by-construction gaps FIRST). The list is the convergence backlog; it must never go stale.
- **Keep at least one improvement EXPERIMENT running** where the project has an experiment chain; on each
  result, act (commit the win / revert the regression) AND launch the next, so the loop self-sustains.
- A tick that finds "nothing to do" is itself a signal to look HARDER, never to idle.

#### ANTI-RUT — ESSENTIAL, NON-NEGOTIABLE (a rut is this loop's PRIMARY failure mode)
A rut is **grinding on one axis with no real movement** — running variant after variant of the same idea,
or over-investing in measurement/infrastructure, while the actual target number stays flat. Detecting and
breaking ruts is a REQUIRED part of auto-steer, checked EVERY tick. It is not optional polish; it is the
difference between converging and spinning.

- **Track the last few outcomes per axis.** If the last **2–3 experiments on ONE axis** came back
  parity / no-improvement / reverted, that axis is **TAPPED OUT — STOP it.** Do NOT build a 4th variant of
  a failed approach. Do NOT keep re-measuring a marginal mechanism with longer/bigger eval runs — that
  *is* the rut wearing a productive costume.
- **RESEARCH FIRST — before building the next thing, and always when an axis stalls.** Go get EXTERNAL
  inspiration with read-only research (WebSearch / WebFetch): how do the best comparable systems (Aider,
  SWE-agent/OpenHands, Cursor, Claude Code) and recent papers actually solve THIS class of problem?
  Translate ONE fitting idea into the project's constraints, then build it. Internal iteration alone
  breeds ruts; the wider field is the way out. (This is the AGENT researching at build-time, never a
  runtime/harness network call.) **Research-first is the default opening move of any new push.**
- **SWITCH AXES, don't grind.** Vary the KIND of work: a genuinely different/bigger capability mechanism
  (decomposition, retrieval/context, planning) vs evals vs tools vs orchestration/wiring vs
  spec/compliance. Wins → double down; stalls → change axis. Never run the same play repeatedly and lose.
- **The metric is MOVEMENT, not motion.** Long eval runs, dashboards, monitoring, and micro-tweaks can
  feel like progress while the real number is flat — that is the classic rut. If you've spent a stretch
  measuring/tweaking without the target moving, STOP, research, switch.
- **A plateau is a harness/scaffolding gap, never a model "ceiling"** (a forbidden conclusion). The exit
  is a richer or different mechanism found by research + axis-switching — not a 4th tweak, and not surrender.
- **Self-check each tick:** "Has the target number moved recently? Am I about to run another variant of a
  thing that already came back parity? When did I last bring in an outside idea?" If the answers smell
  like a rut, research and switch BEFORE doing more of the same.

### 4. Execute via the Jarify workflow — NO ad-hoc edits
Every change — a compliance fix, a conflict resolution, or the next improvement — flows through Jarify:
- `jarify-manage-specs` / `jarify-manage-tasks` / `jarify-manage-links` for the spec docs + traceability.
- the **jarify-builder** agent to implement a task (one builder per task, strictly scoped: writes code,
  runs tests, updates traceability, reports).
- the **jarify-architect** agent to validate (requirement match, design conformance, no regressions,
  strict scope, traceability) and COMMIT when it passes.
- Spec + code change in the SAME commit (spec-first; stale specs are defects).

## Operational guardrails (non-negotiable)
- **PARALLEL / OVERLAPPING WORK IS ENCOURAGED FOR VELOCITY (owner directive, 2026-07-07 — supersedes the
  earlier "sequence behind concurrent work / don't-double-run" rule).** To reach the Prime-Directive
  end-state as fast as possible, run MANY builders/experiments concurrently. The ONE preserved safety
  property is **no two concurrent writers touch the SAME file** — partition parallel work by FILE (or use
  worktree isolation) so builders never collide/clobber. Serial sequencing is no longer required; only
  same-file collision is forbidden. Reconcile shared artifacts (e.g. a spec's `index.json`, frontmatter
  `status`) at integration time.
- **JETSON-UTILIZATION DOCTRINE (owner directive, 2026-07-07):** the Jetson (inference) is the ONE scarce
  resource. MAXIMIZE off-Jetson work (spec authoring, building deterministic tools, tests, code, graders,
  measurement harnesses, governance, research) — parallelize it massively ahead of time so the Jetson is
  never idle waiting on prep; run ON-Jetson experiments (live builds, evals, held-out measurements) in
  BATCHES at full utilization, each with a pre-registered kill criterion.
- READ-ONLY auditing is safe anytime. A CODE change is safe as long as no OTHER concurrent writer is in
  the same file; on a genuinely shared single resource (one GPU mid-run, one shared checkout), still apply
  at a safe boundary. Spec-doc-only changes are safe anytime.
- Where the project runs an improvement-experiment chain, keep MULTIPLE experiments/builders running so the
  loop self-sustains at high throughput; act on each result (commit/revert) and launch the next.

## Notifications & autonomy
The loop runs AUTONOMOUSLY — the **default is to ACT per the intent, not to ask.** Auto-steer and
resolve by the spec / Prime-Directive intent so the user is NOT bothered when it isn't necessary;
interrupting the user for routine progress is itself a failure of the loop's purpose. But when a
push/notification channel is available, **SURFACE what the user genuinely should know** — send a
notification for a SIGNIFICANT event:
- a significant **WIN or milestone** (a real committed improvement and what it moved; an
  external-benchmark result);
- a genuine **QUESTION or DECISION the loop cannot resolve from the intent** and that actually needs the
  user (a true ambiguity, an unresolvable conflict, an irreversible or outward-facing action);
- a **REGRESSION, breakage, or unrecoverable failure**, or a should-have-but-didn't (the chain stalled,
  no net progress in a long while);
- anything the project's **intent explicitly says must be surfaced.**
Do NOT notify for routine, healthy progress. Respect any notification policy the project's intent
specifies (e.g. quiet hours, digests, channels, time zone). The bias is strong autonomy + sparing,
high-signal notifications: act on intent; interrupt the user only when it is significant or genuinely
needed.

## Cadence
Run every ~30 minutes and RE-ARM the next tick (e.g. a scheduled wake-up) so the loop continues
unattended. **The self-re-arm prompt you write for the next tick MUST carry the standing reminder:
"continue using the Jarify skills for EVERYTHING (no ad-hoc edits) — Jarify is how we harness the model
to build the system; and the `.jarify/ROADMAP.md` is what we EXECUTE near AND far term, via the Jarify
skills, to converge on the intent of the Prime Directive."** Keep that reminder in every governance-loop
wake prompt so it survives context loss. Each tick, report concisely: what compliance found/fixed, what
conflicts were resolved by which intent, and what next change was queued or made through the Jarify
workflow — so the trend (not a feeling) is visible.
